# Task: VR-031 — Authoritative edit validation and per-chunk revision

## Goal
A single authoritative writer for block edits. DoD (BACKLOG): concurrent edits serialized.

## Prerequisites / relevant docs
VR-020, VR-030 (`EditValidator`). ADR-002, CONTRACTS (EditIntent, ChunkMutationBatch: idempotent operation ids, bounds-checked indices), GAMEPLAY_RULES (Building, Multiplayer abuse), PERSISTENCE_SECURITY (Commit protocol, Concurrency: single writer, deterministic order, backpressure), QUALITY_GATES (two clients edit same block: serialized result, one chunk revision chain).

## In scope / out of scope
In: `EditIntent` / `ChunkMutationBatch` / `BlockChange` / `EditResult` contracts, `WorldAuthority` (validation with server-side actor pose, per-block stale detection, revision assignment, idempotent operation ids with bounded memory, per-actor token-bucket rate limit, bounded per-tick queue), new rejection codes.
Out: durable journal and "saved" acknowledgement (VR-032; results here are applied, not durable), network RPC/broadcast and join/delta sync (VR-033, with the networked voxel world), multi-chunk operations/explosions (DES-004), permissions/ACL (SAVE-004), inventory.

## Public interfaces and contracts
- `WorldAuthority.Submit(actorId, intent, actorEye, occupants, serverTick, now) → EditResult`. Order of checks: per-tick queue cap (`server_busy`) → per-actor rate (`rate_limited`, 10/s, burst 10) → action supported (`unsupported_action` for Rotate) → index bounds (`invalid_index`) → chunk loaded (`chunk_not_loaded`) → `expectedRevision > current` (`invalid_revision`) → target block changed after `expectedRevision` (`stale_revision`) → shared `EditValidator` rules.
- Each accepted operation changes exactly one block and advances that chunk's revision by exactly 1 (`newRevision = baseRevision + 1`).
- Idempotency: accepted and final rejections are remembered per operation id (bounded, oldest evicted); `rate_limited`, `server_busy`, `chunk_not_loaded` are transient and retryable with the same id.
- Actor pose and occupants must come from server state; intents carry no position.

## Tests (`Tests/Domain/World/WorldAuthorityTests.cs`)
Contiguous batch; same-block concurrency (first wins, second `stale_revision`, one revision); different blocks in one chunk both accepted (per-block staleness); duplicate id idempotent (no double apply); forged future revision; out-of-range indices; unloaded chunk and Rotate; reach from server-side pose; rate limit per actor (others unaffected); transient retry with the same id; bounded per-tick queue; **DoD property test**: 4 actors, 4,000 seeded interleaved and colliding intents with stale views → accepted batches form one gap-free revision chain, and replaying them reproduces the authority's chunk hash and revision.
