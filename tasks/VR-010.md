# Task: VR-010 — Touch Input System action maps

## Goal
Landscape touch driving controls on the Input System. DoD (BACKLOG): steer + gas simultaneous, landscape safe area.

## Prerequisites / relevant docs
VR-001 (Input System only, landscape), CONTROLS_ASSETS (action map, layout, adjustable size/sensitivity, accessibility), CONTRACTS (ClientInput ranges), skills/unity-gameplay.

## In scope / out of scope
In: `Driving` action map (Steer, Throttle, Brake, Boost, Handbrake, BuildMode, Look), landscape touch HUD inside the safe area, steering ramp for digital buttons, control settings model, wire quantization of input, multi-touch DoD test.
Out: sending input to the server (VR-012), vehicle response (VR-011), settings UI and persistence (SAVE-008), build-mode controls (VR-030), final art, tilt controls, haptics.

## Public interfaces and contracts
- Core (engine-free): `DrivingInput` (steer [-1,1], throttle/brake [0,1], NaN → 0, unknown button bits dropped), `QuantizedDrivingInput` (CONTRACTS ClientInput: steering int16 ±1000, throttle/brake uint16 0..1000, flags uint8; `IsValid`/`TryToInput` reject out-of-contract wire data), `SteeringFilter` (turn-in rate, faster return/reversal), `ControlSettings` (sensitivity 0.5–2, button scale 0.75–1.5), `SafeAreaLayout.Compute`.
- Presentation: `DrivingControls.CreateMap()` (action map defined in code), `DrivingInputReader` (`Current`, `RawSteer`, `Look`, `BuildModePressedThisFrame`, `Apply(ControlSettings)`), `SafeAreaFitter`, `TouchControlsScaler`.
- Client scene: `EventSystem` + `InputSystemUIInputModule`, `DrivingInput`, `TouchHud` canvas (1920×1080 reference, match height) → `SafeArea` → left cluster (◀ ▶), right cluster (BRAKE, GAS, DRIFT, BOOST), top centre (BUILD).

## Design notes
- Touch buttons are Input System `OnScreenButton`s emulating virtual gamepad controls (`<Gamepad>/dpad/left`, `rightTrigger`, ...), so touch, gamepad and keyboard share one action map; multi-touch comes from the UI module's per-touch pointers.
- The action map is built in code: reviewable in diffs and testable; player rebinding can use Input System binding overrides later. `ProjectConfiguration` now removes and validates against a project-wide actions asset (the template left a dangling reference).
- Steering from digital buttons ramps to full lock in 0.25 s at sensitivity 1 and returns twice as fast, instead of snapping.
- Buttons carry text labels as well as colours (not colour-only).

## Failure modes / security concerns
- Input values are clamped and NaN-safe before reaching simulation; quantized wire input outside the contract decodes to neutral and is reported invalid (the server will reject it in VR-012).
- Degenerate or off-screen safe areas fall back to full screen rather than collapsing the HUD.

## Unit tests
Domain: `DrivingInputTests` (clamping, NaN, button masking, quantization rounding/round-trip, out-of-contract rejection), `SteeringFilterTests` (ramp, faster return, reversal, NaN/zero delta, settings validation), `SafeAreaLayoutTests` (notch insets, full screen, clamping, degenerate input).

## Integration tests (PlayMode)
- `TwoSimultaneousTouches_SteerLeftAndGas_BothRegister`: **DoD**. Two concurrent touches on the real HUD through EventSystem → OnScreenButton → action map; steer reaches −1, gas 1; releasing steer returns it to centre while gas stays held.
- `Gamepad_SteerAndTriggerTogether_BothRegister`: stick + trigger + boost together.
- `Hud_IsInsideSafeAreaAndLandscapeAnchored`: every control's centre inside `Screen.safeArea`; steering left, gas right.
- Batch-mode note: a headless editor never has app/Game View focus, so the touch test sets `backgroundBehavior = IgnoreFocus` and `editorInputBehaviorInPlayMode = AllDeviceInputAlwaysGoesToGameView` for its duration (restored after). `InputTestFixture` wasn't used: its input-system reset conflicts with the HUD's on-screen devices during teardown.
