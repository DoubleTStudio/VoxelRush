# Task: CI-002 — Full-suite regressions on main

## Goal
Make the first full-suite run on main (after CI-001) green, and make it report every regression in one run.

## Findings (main runs 39575225589, 39579119603)
- **Run cancelled by the next merge.** The workflow-level `cancel-in-progress: true` also applied to pushes to main, so merging #44 killed the CI-001 full suite after 30 min (it had passed through the chunk-cache test).
- **Loss test failed: "race never reached Finishing".** The 8-bot race at 2% loss ran with the server at 2–20 Hz (`tickRate` in `server_tick_metrics`) while its own tick work stayed at p50 0.3 ms: the server was starved of CPU, not slow. The bots finished their 48 s smoke window before anyone completed a lap. The same signature (13–20 Hz at 8 players, p50 0.3 ms) is in the earlier main load-test failure (run 39539299740).
- **Root cause:** headless bots (`Bot.unity`) had no frame cap. A batchmode player without vsync runs its frame loop uncapped, so each of 8 bots spins a core on a 2-vCPU runner. The server caps itself at the 30 Hz tick; the phone client is capped by `QualityController`, which `Bot.unity` does not have.
- **Hidden by step gating:** the loss test failing skipped destruction stress, the load test, the Android APK and iOS, so their state on main was unknown.

## Changes
- `BotInputSource.Awake`: batchmode players (not the editor) set `vSyncCount = 0` and `targetFrameRate` to the high-tier phone rate (60, `QualityPresets.For(High)`) and log `event=bot_frame_cap`. A 30 fps cap (the tick rate) was tried first: load held 30 Hz, but frame quantization raised the drive test's ack latency at 100 ms RTT from ~185 ms to 235–266 ms, over its 250 ms bound, so the bound stays and the cap is 60.
- `ci.yml`:
  - `cancel-in-progress` only for pull requests; a push to main waits for the running full suite.
  - End-to-end steps after the bot build run with `!cancelled()` (gated on the bot build), so one failing test no longer hides the rest. Android and iOS builds run regardless of test results; image publish still requires every earlier step to pass.
  - `compile-ios` runs when the Xcode project was packaged (job output `ios`), even if an end-to-end test failed.
- No thresholds changed: load test still requires ≥ 29 Hz, p95 ≤ 33.3 ms and ≤ 1% overruns at 8 players; the loss test still races 8 bots.

## Not done
- PR runs and main runs share the `unity-personal-license` concurrency group; GitHub keeps one pending job per group, so a queued main Unity job can be replaced by a later PR's. Avoiding that needs a second license seat or a queueing runner.

## Verification
- actionlint 1.7.7 clean on `ci.yml` and `release.yml`.
- `dotnet test tests/VoxelRush.Domain.Tests`: 465 passed.
- Unity compile, loss, stress, load, Android: the `full-ci` PR run (Docker smokes run only on Linux x86-64 CI).

## Risks / rollback
Bots now run at most 60 frames/s; prediction and race logic step on the 30 Hz tick, so behaviour is unchanged, but a test that relied on many frames per tick would slow down. Main pushes now queue instead of cancelling, so a burst of merges runs the newest one after the current suite. Rollback: revert.
