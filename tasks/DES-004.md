# Task: DES-004 — Bounded explosion and chunk mutation batching

## Goal
Server explosions that stay within a radius and block budget and commit as consistent per-chunk batches. DoD (BACKLOG): 256-block fixture consistent.

## Prerequisites / relevant docs
DES-001..003, VR-031..033 (authority, journal, replica). DESTRUCTION (Explosion: bounded radius falloff and max block budget; Failure handling: refuse rather than ack unsaved changes; Tests: explosion bounds, late join), CONTRACTS (ChunkMutationBatch per chunk).

## In scope / out of scope
In: `ExplosionModel` (max radius 4, max damage 400, budget 256 blocks — placeholders except the budget), `ExplosionResolver`, `DamageLedger`, `WorldAuthority.CommitServerChanges` (multi-chunk, all-or-nothing, idempotent operation id), `IMutationSink.CanAcceptMany`.
Out: what triggers explosions (gameplay items/hazards, M5), explosion VFX event (DES-005), HP replication/persistence (journal record v2), support/collapse checks after removal (DES-010/011), mesh/collider rebuild priority (DES-012), sending explosions over the network.

## Design notes
- **Plan, then commit**: candidates (solid, destructible, loaded, zone allows damage) within the clamped radius are sorted nearest-first with a positional tie-break, cut at the budget, and their removals grouped by chunk. The authority checks every chunk is loaded and the journal has room for all batches **before** touching anything; only after a successful commit is HP updated. A refused blast changes neither blocks nor HP.
- One `ChunkMutationBatch` per changed chunk, all sharing the operation id, each contiguous with the chunk's previous revision (one revision per changed block, like client edits), so replicas and journal replay need no new rules.
- Server commits record per-block last-change revisions, so client edits aimed before a blast are rejected as stale.

## Tests (`Tests/Domain/Destruction/ExplosionTests.cs`)
- **DoD**: a server-built 12×8×12 brick cube across four chunks; radius-4 blast hits exactly **256** blocks (budget cut, ~268 in range), destroys the near ones, cracks the rest; one batch per chunk (4), contiguous revisions, removals only inside the radius; a replica fed snapshots + all batches ends with identical hashes and revisions, no gaps.
- Determinism; radius/damage clamping and invalid input; integer falloff; protected zones and indestructible blocks survive; cracked blocks keep HP for the next blast; journal backpressure changes nothing (blocks or HP); server-commit idempotency and all-or-nothing on an unloaded chunk; blasts make earlier client edits stale.

## Bug found later (fixed here)
DES-003's `ImpactResolver` destroyed blocks with `ChunkData.Set` directly, so a collision kill would be neither journaled nor replicated (found while testing the VR-061 race overlay). Now that `CommitServerChanges` exists, the resolver works on a `WorldAuthority` + `DamageLedger`: HP-only hits stay in the ledger, a destroying hit is committed through the authority (and refused without touching HP under journal backpressure). Tests: kill journaled with the car as actor, backpressure leaves block and HP, unloaded chunk refused (domain 313/313 at this commit).
