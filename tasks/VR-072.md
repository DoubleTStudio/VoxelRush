# Task: VR-072 — Network bandwidth/interest optimization and loss testing

## Goal
Measure and reduce what the server sends, and prove the game holds up on a lossy network. DoD (BACKLOG): stable at 2% loss fixture.

## Prerequisites / relevant docs
VR-012/013 (vehicle netcode, load fixture), VR-033 (world sync), VR-062 (race flow). VEHICLE_NETWORKING (tests: loss, jitter), PERFORMANCE, QUALITY_GATES.

## In scope / out of scope
In: real packet loss/delay inside Unity Transport for dev builds (`-simTransportLossPercent`, `-simTransportDelayMs`; `LossyDriverConstructor` appends UTP's `SimulatorPipelineStage` to every NGO pipeline, send and receive), distance-tiered vehicle snapshots per client (`SnapshotInterest`: < 80 m 15 Hz, < 200 m 7.5 Hz, beyond 5 Hz; owners always 15 Hz), adaptive interpolation delay for sparse snapshots, `BandwidthMeter` + `net_bandwidth` logs, `BOT_ARGS` pass-through and `tools/smoke-loss.sh` (CI on main).
Out: interest for world deltas/snapshots (the plot is 72 chunks; needed with large worlds and VR-023 streaming integration), delta-compressing snapshots, transport-level byte counters, mobile network profiling on devices.

## Design notes
- NGO 2.x's `SetDebugSimulatorParameters` is a no-op, so the simulator stage is inserted through NGO's `INetworkStreamDriverConstructor` hook; only bots (clients) enable it, which drops 2% of packets in each direction for that client, reliable channels included (NGO must resend), unlike the game-layer `-simLossPercent` that only touched vehicle messages.
- Interest is computed per snapshot per client from the server-side distance between this car and that client's car; tier rates keep a boosting car's movement between updates under the 10 m teleport threshold. Remote interpolation waits 1.5 snapshot intervals when snapshots arrive slower than the configured delay.

## Results (`docs/perf/VR-072-bandwidth-loss.json`)
- 8-bot load test: interest management skipped 15,352 snapshot deliveries = **40.7%** of snapshot payload; per-client downstream peaked at 7.8 KB/s and fell to 3.5 KB/s as cars spread. 8-car race pack: 8.4 KB/s per client (all cars near, full rate). Tick metrics unchanged (p95 1.72 ms, 0 overruns).
- **2% loss**: drive (mean prediction error 0.037 m, 0 snaps, cheat rejected), world sync (late join + restart hashes), 8-player race (8/8 finished, reconnect, identical results) all pass.
- Observations (not regressions): the transport simulator adds ~80 ms to input→ack (121 → 201 ms) beyond what 2% loss explains; the 8-bot load test's mean ack latency varies 149–202 ms run to run on one machine, before and after this change.

## Bugs/issues found during validation (fixed)
- The adaptive delay first stretched full-rate streams (spacing equal to the delay): now only when spacing exceeds the delay by 5%. Three interpolator tests caught it.
- Drive test's remote-snapshot floor (≥ 200) assumed full rate for a car that drives away; lowered to ≥ 100 with the reason.
- Load test's "8 distinct spawn points" check was too strict (bots drive off immediately, later bots reuse freed slots); it now checks every car spawned on the grid row (the VR-012 bug it guards against).
